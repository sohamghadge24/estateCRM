1. Executive Summary
EstateOS is a commercial-grade, multi-tenant real estate CRM and property operations platform for independent agencies, brokerages, property consultants and multi-branch businesses. It combines CRM, property inventory, listing publication, enquiry handling, appointments, deals, commissions, communications and agency reporting.
The product has three distinct surfaces: Agency Workspace for owners, managers and agents; Public Property Portal for customers discovering listings and submitting enquiries; and SaaS Platform Administration for the EstateOS operator to manage agency tenants, plans, subscriptions, entitlements and platform health.
The recommended implementation is a modular monolith using FastAPI, React/TypeScript, PostgreSQL with PostGIS, Redis and Celery, S3-compatible object storage and Docker Compose. This keeps the first release deployable on an affordable VPS while preserving module boundaries for future scale.

1.1 Planning assumptions
Shared platform with shared PostgreSQL schema and tenant_id isolation for agency-owned records.
A global person account may have memberships in multiple agencies; roles are assigned per membership.
The first release is a modular monolith, not microservices.
Public listing access is separated from private CRM, customer, deal and financial data.
Payment, email, SMS, WhatsApp, calendar and map services are integrations selected during discovery.
SaaS subscription billing must remain separate from agency property transactions, customer payments and agent commissions.

5.1 Technology decisions
PostgreSQL is authoritative; Redis is disposable infrastructure.
Keep providers behind adapters so messaging, maps, storage and payments can change.
Use a modular monolith first; extract services only when evidence justifies it.
Use SSR/SSG for search-engine-visible listing pages; private CRM may remain a Vite SPA.
6. Technical Architecture
Requests enter through a reverse proxy that routes the public portal, private workspace and API. FastAPI owns authentication, tenant context, business rules, authorization and transactional writes. MYSQL stores operational records. Redis supports caching and task brokering. Celery workers execute asynchronous work. Object storage stores media and documents outside the relational database.

6.1 Architecture principles
Tenant-aware by design: tenant_id and PostgreSQL RLS protect agency-owned records.
API-first: web clients and integrations use versioned contracts, never direct database access.
Each domain owns models, schemas, repositories, services, routers, events and permissions.
Persist critical business state and outbox event in one transaction.
Run exports, imports, media processing and notifications asynchronously.
Store object keys privately; issue short-lived signed access after authorization.
One deployable backend initially, with clear module boundaries.

Tenant selection and active membership validation.
Role permission plus own/team/branch/tenant scope evaluation.
Lead assignment, qualification, duplicate merge and pipeline transitions.
Property/listing lifecycle and publication approval.

Deal offers, booking, payments and commission calculations.
Plan entitlements and quota enforcement.
Document access, retention and export authorization.
10.2 Transaction and event pattern
Persist business state and outbox event in the same PostgreSQL transaction. Workers dispatch notifications, webhooks and follow-up jobs. Consumers must be idempotent, retries bounded and failed events visible for review. Do not rely on in-memory events for durable workflows.

11.2 Cross-cutting API requirements
Requirement
Standard
Transport
HTTPS only in production; TLS 1.2+; no secrets in query strings.
Authentication
Short-lived access token and rotating refresh tokens; secure HttpOnly cookies and CSRF protection for cookie sessions.
Authorization
Role permissions plus own/team/branch/tenant scope on every protected request.
Tenant context
Derive from authenticated membership; never trust client tenant_id as authorization.
Versioning
/api/v1; breaking changes require a new version and deprecation plan.
Idempotency
Use Idempotency-Key for payments and retry-sensitive writes.
Time
Store UTC timestamps; preserve tenant timezone for display/business rules.
Pagination
Document page/cursor pagination, max page size and allowlisted filters/sorts.
Errors
Consistent code, message, field errors and request_id; no stack traces.
Uploads
Controlled/pre-signed uploads; validate MIME, size, checksum and ownership.
Rate limits
Per-user, IP, tenant and integration-client limits.
Audit
Log privileged writes, exports, role changes, billing and sensitive document access.
OpenAPI
Review schemas and examples; publish dev/UAT documentation.

12.2 Multi-tenant isolation
Use shared database/shared schema with tenant_id on tenant-owned tables. Use composite foreign keys and tenant-aware indexes. Apply PostgreSQL RLS to every tenant-owned and association table. The application DB role must be non-superuser and lack BYPASSRLS.
ALTER TABLE leads ENABLE ROW LEVEL SECURITY;\nALTER TABLE leads FORCE ROW LEVEL SECURITY;\nCREATE POLICY tenant_leads_policy ON leads\nUSING (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid)\nWITH CHECK (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid);\n-- Set tenant context transaction-locally after membership validation.
12.3 Core relationships
users 1---* memberships *---1 tenants\nmemberships *---* roles (membership_roles)\nroles *---* permissions (role_permissions)\ntenants 1---* branches 1---* teams\ntenants 1---* leads *---1 contacts\ntenants 1---* properties 1---* listings\nlistings 1---* enquiries *---1 contacts\ndeals *---1 property; deals *---* contacts; deals 1---* offers/payments/commissions
12.4 Data design rules
Use UUIDs, tenant_id, timestamps and created_by where appropriate.
Use archival/soft deletion for important business records; preserve financial/audit history.
Use decimal types for money and ISO currency codes, never floating point.
Store timestamps in UTC and tenant timezone for display/business cut-offs.
Use JSONB for flexible agency attributes, not core relational fields.
Use PostGIS GiST indexes for spatial search and combine with tenant filters.
Use tenant-aware unique constraints and indexes.

Appendix A - API Conventions and Sample Payloads
A.1 Query and pagination example
GET /api/v1/leads?status=qualified&branch_id=<uuid>&limit=25&cursor=<opaque-cursor>&sort=-created_at
Use allowlisted filters and sort fields. Reject unknown sort expressions. Return a stable cursor and do not expose internal SQL/ORM field names.
A.2 Create-lead payload
{\n  "name": "Rahul Sharma", "email": "rahul@example.com",\n  "phone": "+919876543210", "source": "website",\n  "property_type": "apartment", "budget_min": 5000000,\n  "budget_max": 8000000, "city": "Mumbai"\n}
The server determines tenant, creator membership and ownership. Client-supplied tenant_id is not accepted as authorization.
A.3 Standard success response
{ "data": { "id": "resource-uuid", "status": "new" },\n  "meta": { "request_id": "req_...", "timestamp": "2026-11-04T06:30:00Z" } }
A.4 Standard error response
{ "error": { "code": "permission_denied",\n  "message": "You do not have permission to assign this lead.",\n  "field_errors": {}, "request_id": "req_..." } }
A.5 Router pattern
api_v1 = APIRouter(prefix="/api/v1")\napi_v1.include_router(auth.router, prefix="/auth")\napi_v1.include_router(leads.router, prefix="/leads")\napi_v1.include_router(properties.router, prefix="/properties")\napi_v1.include_router(billing.router, prefix="/billing")\napp.include_router(api_v1)
Routers validate requests, call application services and return response schemas. Business rules belong in services; data access belongs in repositories.
